# Aino Selection Console V3

Standalone Vercel deployment for the Aino Home Selection Console, integrating the existing Selection Engine and Pricing Intelligence Engine with the AliExpress Product Acquisition Engine.

## V3 integration

### Selection Engine

The existing Selection Engine remains in `api/assess.js` and uses the existing DeepSeek API configuration. The frontend sends the same authenticated requests as the previous console.

### Storage

`api/storage.js` remains backed by Upstash Redis through `@upstash/redis` and retains the existing `APP_PASSWORD` authentication contract.

### Product Acquisition Engine

`api/acquisition.js` is a Vercel serverless function using the same POST + `x-app-password` authentication pattern as the existing API endpoints.

Input:

- AliExpress full product URL
- AliExpress short URL

Default operating destination:

- Finland (`FI`)

Default normalized currency:

- EUR

The acquisition flow is:

```text
AliExpress URL
    ↓
POST /api/acquisition
    ↓
AliExpress adapter
    ↓
Raw supplier evidence
    ↓
Aino Product Record
    ↓
Mandatory-field validation
    ↓
COMPLETE / PARTIAL / CONFLICTING / FAILED
```

### Acquisition evidence integration

A successful acquisition creates an `acquisition_record` evidence item in the product record. This evidence is generated by the acquisition engine and is not an ordinary editable evidence card.

The console deliberately preserves `acquisition_record` during `syncEvidencesFromDOM()` so normal intake editing cannot accidentally delete the acquisition evidence before Selection runs.

### Full Assessment flow

The `Source product URL` field is the canonical entry point for an AliExpress product.

When `Run Full Assessment` is clicked with an AliExpress URL:

1. The console checks whether acquisition has already been run for that URL.
2. If not, it calls `/api/acquisition` automatically.
3. If acquisition is not `COMPLETE`, Selection and Pricing remain blocked.
4. If acquisition is `COMPLETE`, its acquisition record is retained as evidence.
5. Selection runs using the resulting evidence.
6. Pricing runs independently using the selected transaction scenario.

The old `Add at least one evidence source` gate therefore does not block an AliExpress acquisition that has already produced the required evidence record.

## Environment variables

Set these in Vercel → Settings → Environment Variables:

### Required

- `APP_PASSWORD` — access password used by `/api/storage`, `/api/assess`, and `/api/acquisition`
- `DEEPSEEK_API_KEY` — DeepSeek API key used by Selection/Pricing assessment
- `KV_REST_API_URL` — Upstash Redis REST URL
- `KV_REST_API_TOKEN` — Upstash Redis REST token
- `FETCHLAYER_API_KEY` — API key for the AliExpress product-detail adapter

### Optional

- `DEEPSEEK_MODEL` — defaults to `deepseek-flash`
- `DEEPSEEK_REASONING_EFFORT` — existing Selection setting; defaults to `high`

The acquisition endpoint itself requests EUR output from the acquisition provider. Source currency should still be preserved by the acquisition record when available.

## Deployment

1. Push the entire folder to the GitHub repository.
2. Keep the `api/` directory at the Vercel project root, or set Vercel Root Directory to the directory containing `index.html` and `api/`.
3. Set all required environment variables above.
4. Ensure the Upstash Redis integration remains connected.
5. Redeploy.

Do not deploy only `index.html`. The API functions must be deployed in the same Vercel project:

```text
/api/assess
/api/storage
/api/acquisition
```

## Acquisition provider

The current AliExpress adapter uses the configured FetchLayer product-detail endpoint. The adapter is isolated from the rest of the engine so another authorized/API/browser adapter can be introduced later without changing the Product Record contract.

The architecture intentionally does not treat this as a brittle HTML scraper.

## Acquisition status rules

- `COMPLETE` — mandatory acquisition fields are present and validated; downstream analysis may proceed.
- `PARTIAL` — one or more mandatory fields are missing or cannot be verified; the record is saved but downstream analysis is blocked.
- `CONFLICTING` — supplier evidence contains conflicting mandatory facts; downstream analysis is blocked.
- `FAILED` — acquisition could not produce a usable record.

Supplier-derived acquisition facts remain supplier evidence. They are not automatically upgraded to independently verified facts.

## Important sourcing rule

A supplier stating that an item ships from an EU country does not, by itself, establish EU VAT treatment, customs treatment, or import responsibility. Those trade fields must be supported separately before the acquisition record becomes downstream-eligible where the validator requires them.
